Production deployment ​

This example uses Linux, systemd and Caddy on the same host. It assumes a domain, a server and an installed Caddy. Adapt paths, users and domain names. These service files are recommended examples, not an installer shipped by GooseForum.

Stable paths and service identity ​

Place the executable, config.toml and storage/ in /opt/gooseforum, running as a dedicated system account named gooseforum. Create the account and directory, extract the release there, and grant the service account the required read/write access. Do not expose configuration or databases through a web root.

Generate the initial configuration by running from that directory, stop the process, then edit the existing sections:

toml
[app]
env = "production"
# Keep the existing secretKey; do not replace the entire file with this excerpt.

[server]
url = "https://forum.example.com"
port = 5234
trustedProxies = ["127.0.0.1"]

[log]
type = "stdout"

TOML sections cannot be declared twice. Merge these values with existing database and other settings. Restrict config.toml, for example with chmod 600 config.toml, and ensure it belongs to the service account.

Backend listening address

Production HTTP listens on all interfaces. Restrict external access to port 5234 using your firewall or security group, routing public traffic through the HTTPS proxy. server.url does not change the listening address.

Configure systemd ​

Save this example as /etc/systemd/system/gooseforum.service:

ini
[Unit]
Description=GooseForum
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=gooseforum
Group=gooseforum
WorkingDirectory=/opt/gooseforum
ExecStart=/opt/gooseforum/GooseForum serve
Restart=on-failure
RestartSec=5
UMask=0077

[Install]
WantedBy=multi-user.target

WorkingDirectory determines configuration and relative data paths. The user must be able to access databases, logs and backups. Then run:

sh
sudo systemctl daemon-reload
sudo systemctl enable --now gooseforum
sudo systemctl status gooseforum
sudo journalctl -u gooseforum -n 100 --no-pager

Add the HTTPS proxy ​

Add this site block to your Caddyfile, replacing the domain:

text
forum.example.com {
    reverse_proxy 127.0.0.1:5234
}

Point DNS at the server and allow ports 80 / 443 as required for certificate issuance and access. Use Caddy's configuration validator before reloading; see the official reverse-proxy guide. A containerized or remote proxy requires corresponding changes to the backend address and trustedProxies.

Verify the deployment ​

sh
curl --fail http://127.0.0.1:5234/api/forum/status
curl --fail https://forum.example.com/api/forum/status

This checks HTTP access and the deployment-status path. It does not establish database, email or object-storage health. Test registration, login, posting, images, email links and third-party callbacks with the real domain.

For large upload failures, check application upload limits, HTTP timeouts and proxy limits. S3 direct uploads also require bucket CORS; see configuration.

Ongoing operation ​

Keep one service instance and establish the backup and upgrade procedure. Restart after changing ports, databases, logging or the cache backend. File watching does not reinitialize every running subsystem.
