Registration and account security ​

Registration counters, authentication caches and MFA challenges include process-local state. Use a single instance. Connecting multiple processes to the same database does not make those states shared.

Registration and email quotas ​

Settings → Security allows hourly registration-request limits. Defaults are:

DimensionRegistration requestsShared password-reset and verification-email quota
Per trusted IP520
Per target email33
Site-wide100200

For configurable registration limits, 0 disables that dimension. Counters measure requests that pass policy and credential checks, not only successfully created accounts. Each in-memory window lasts one hour from its first request; restarting clears it. Counters are not shared across instances. Verification resends also have account limits of once per minute and three times per day.

Allowed email domains use exact matching: example.com does not allow sub.example.com. Accounts created with verification requirements retain those requirements; switching to OAuth does not bypass them.

Client IPs behind a proxy ​

Only proxy IPs or CIDRs in server.trustedProxies are trusted. For an IPv4 reverse proxy on the same host, add this to the existing [server] section:

toml
trustedProxies = ["127.0.0.1"]

Without this configuration, forwarded headers are not trusted and requests may share the proxy's IP for rate limiting. Do not trust every address. For containers or separate proxies, list the actual controlled proxy addresses and restrict direct backend access. See deployment.

Enable two-factor authentication ​

GooseForum supports standard TOTP codes (six digits, 30 seconds) and ten single-use recovery codes. Enabled MFA applies to both password and OAuth login.

  1. In account settings, enter the local account password to begin binding an authenticator.
  2. Scan the QR code or enter its secret manually, then confirm with a code. Binding is not active before confirmation.
  3. Save the recovery codes, which are displayed once and can be downloaded.
  4. Sign in again to verify. Enabling, disabling or regenerating recovery codes revokes logins on all devices.

OAuth users must first bind and verify an email address, then set a local password through the password-reset flow. Resetting a password does not disable MFA. Each recovery code works once; generating a new set invalidates all old codes.

System secret and time ​

[app].secretKey is used to derive the MFA encryption key. Keep its generated random value and back it up with the database. If the new field is absent, old signingKey configurations are supported; retain the exact value when renaming the field.

Do not replace the secret with a memorable password or regenerate it after users have enrolled. A lost or malformed key causes verification to fail; generating another configuration cannot decrypt existing data. Keep both server and authenticator clocks synchronized.

Login challenges expire in five minutes and pending enrollment in ten minutes. Restarting the server requires a new login or enrollment attempt. TOTP codes cannot be reused.

Recover a lost authenticator ​

Use an unused recovery code first. If all second factors are lost, a full administrator can verify identity and reset MFA under Users → Edit → Account settings, providing a reason and confirmation. The operation revokes sessions and writes an audit record. A limited user administrator cannot do this, and an administrator cannot use this entry point to reset their own MFA.

There is currently no MFA-reset CLI or email-only bypass. Preserve the system secret and recovery codes; changing a password is not an MFA recovery procedure.
