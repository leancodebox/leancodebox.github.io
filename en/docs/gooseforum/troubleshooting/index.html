Troubleshooting

On this page

Troubleshooting ​

Record the version, working directory, database type, recent changes and error time before reviewing logs. Remove passwords, cookies, tokens, connection strings and email credentials before sharing diagnostics.

Startup fails or the forum is unexpectedly empty ​

With systemd, inspect systemctl status gooseforum and journalctl -u gooseforum -n 100 --no-pager. Check occupied ports, TOML syntax, file permissions and database availability.

If the service starts with no old topics, check WorkingDirectory, the actual config.toml, the SQLite path or external database name. Do not keep registering, migrating or replacing data before confirming the correct database.

Registration, email or rate-limit problems ​

SymptomCheck
New accounts cannot registerRegistration switch, exact allowed-domain matching, SMTP configuration
First OAuth login failsValid upstream email, conflicts with existing accounts, registration policy
Users appear to share one IPProxy address in server.trustedProxies
Test email works but settings do notTests use current form values; save them afterward
SMTP accepts email but it never arrivesInbox, spam, provider delivery logs and bounces
Unverified account cannot sign inCorrect credentials can trigger resend, subject to cooldown and quotas

Fix configuration and delivery before retrying. Repeated restarts to clear counters do not diagnose the problem. See account security for quota defaults.

MFA verification fails ​

Check server and phone clocks, reused codes and expired login challenges. A restart clears challenges, requiring a new login attempt.

If all enrolled users fail after an upgrade, first check whether [app].secretKey or the old signingKey changed. Restore the original value; a new key cannot decrypt existing data. Follow recovery guidance for a lost authenticator. Password reset does not remove MFA.

Images or attachments fail ​

For database storage, check the connection and file records. For S3, separately inspect the server endpoint, credentials, bucket, browser-facing publicUrl and object permissions.

For direct uploads, inspect the presigned PUT in browser network tools. Bucket CORS must allow the site origin, PUT and Content-Type. Timeouts also require checking application HTTP timeouts, file-size rules and proxy limits.

Inconsistent pages after deployment ​

Confirm frontend and backend belong to the same build, the running executable was replaced, and the proxy is not retaining stale HTML or status responses. Save drafts before refreshing. Rebuilding frontend files alone does not update resources embedded in an old binary.

Administrator account recovery ​

A server administrator can use these commands from the original working directory. 42 is a placeholder user ID and must be checked first:

sh
./GooseForum set-user-admin 42
./GooseForum set-user-password 42 'REPLACE_WITH_A_NEW_PASSWORD'

Run only the operation required and replace the example password. Command-line passwords may appear in shell history and process arguments; use a controlled maintenance terminal. A separate CLI password change can take up to 15 seconds to invalidate the running service's authentication cache. Neither command resets MFA.

Report a reproducible issue ​

Include version or commit SHA, OS and CPU, database type, reproduction steps, expected/actual behavior and sanitized logs. For UI failures, include browser version and failed request status codes. Report at GooseForum Issues.
