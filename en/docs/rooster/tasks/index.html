Task configuration and execution ​

Create a disabled task first, run it manually and inspect logs before enabling automation. Enabled means supervision or scheduling is active; running means a command is executing. They are separate states.

Choose a task type ​

BehaviorResidentScheduled
Intended useDevelopment servers, long-running workersPeriodic checks, synchronization, scripts
EnableStarts supervisionRegisters Cron
DisableStops supervision and requests stop for managed executionsCancels future triggers; existing runs continue
Manual runAvailable, including while disabledAvailable, including while disabled

Use scheduled tasks for short commands that need periodic execution, rather than forcing a resident supervisor to loop them.

Shell and direct execution ​

  • shell supports pipelines, redirection and shell syntax, such as echo ready. A custom shell can be selected.
  • exec takes an executable in command and separate entries in arguments. Do not put a whole shell command in the executable field.

For a development server, an example is mode exec, executable /absolute/path/to/pnpm, arguments ["dev"], and the project's absolute working directory.

An empty workingDir inherits Rooster's working directory. Task environment values override the inherited cached environment. Prefer absolute program and directory paths when depending on interpreters, package managers or PATH. A tray-launched process may not share your current terminal environment.

Cron and overlap ​

The five fields are minute, hour, day of month, month and day of week. This is not a six-field expression with seconds.

ExpressionMeaning
*/15 * * * *Every 15 minutes
0 3 * * *Daily at 03:00
0 9 * * 1-5Weekdays at 09:00
CRON_TZ=Asia/Shanghai 0 9 * * *Daily at 09:00 in Shanghai time

The default timezone is the process's local timezone. Descriptors such as @hourly are also accepted. Check the next five trigger times shown by the console.

overlapPolicy defaults to skip, preventing a new overlapping execution. parallel allows concurrency. Ensure tasks that modify the same files or data can run concurrently. A conflicting manual run returns 409; it does not wait in a queue.

Resident restart policy ​

SettingMeaning
restartPolicy: on_failureDefault; restart on failure
restartPolicy: alwaysRestart automatically
restartPolicy: neverDo not restart automatically
maxRetriesConsecutive-failure limit; omitted or 0 becomes 3
minRunSecondsMinimum normal runtime; omitted or 0 becomes 10 seconds

The supervisor treats a nonzero exit or a runtime shorter than minRunSeconds as failure. A quick exit with code 0 can therefore have a successful execution record while the supervisor treats the short run as a failure and retries. Reaching the consecutive-failure limit disables the task. maxRetries=0 does not mean unlimited retries.

Stop, edit and delete ​

The edit entry point remains available, but enabled or running tasks show read-only configuration. Disable the task, wait for or stop active executions, confirm none remain, then reopen the editor and save. Deletion has the same preconditions.

Disabling a scheduled task does not stop a current execution. Stopping a scheduled execution does not cancel future triggers. Stopping an enabled resident execution also disables supervision; manually started executions may require a separate stop.

Instance-wide limits ​

Set these variables when starting Rooster. Zero or unset disables each limit:

VariableMeaning
ROOSTER_MAX_CONCURRENTMaximum active or starting executions across the instance
ROOSTER_MAX_PER_TASKMaximum concurrent executions per task
ROOSTER_EXECUTION_TIMEOUTTimeout for all execution types, for example 30m

At capacity, manual requests return 409 and are not queued. Timeouts are recorded as failures with context deadline exceeded. Consider whether a global timeout is appropriate for resident services.
