备份、升级与恢复 ​

一次有效备份必须能恢复站点数据和运行配置。只有程序压缩包，或只保存 SQLite 文件，都不能覆盖所有部署方式。

需要备份哪些内容 ​

内容为什么需要
config.toml数据库连接、存储配置和系统密钥；MFA 等加密数据依赖原密钥
整个 storage/默认 SQLite、日志和本地备份等运行数据，实际范围取决于配置
外部 MySQL / PostgreSQL不在本地 storage/ 中，需使用对应数据库的备份工具
S3 对象及配置本地数据库备份不会包含桶内文件
当前程序版本与提交用于重建与数据匹配的运行环境

将备份复制到独立存储，限制访问权限。备份中可能包含凭据、用户信息和私密附件。

SQLite 自动备份 ​

在已有 [db] 段检查：

toml
backupSqlite = true
backupDir = "./storage/databasebackup/"
keep = 7
spec = "0 3 * * *"

这表示启用 SQLite 定时备份、保留 7 份，计划时间为每日 03:00。确认运行环境时区、备份目录可写及磁盘空间，并观察实际产物和日志。它不会备份系统密钥、外部数据库或 S3 对象，同机备份也无法应对整机丢失。

手工复制 SQLite 时先停服再复制，避免只复制在线数据库主文件而遗漏 WAL 中的已提交数据。

升级步骤 ​

  1. 阅读目标 Release，记录当前版本、运行目录和数据库类型。
  2. 暂停写入并停止服务。使用前文 systemd 示例时执行 sudo systemctl stop gooseforum。
  3. 备份配置、数据库和存储，保留旧程序；外部数据库使用其一致性备份方式。
  4. 在临时目录解压并校验新发行包，只替换程序，保留原配置、密钥与数据目录。
  5. 检查 [db].migration。开启迁移时启动会执行升级所需结构变更；也可在同一运行目录使用 ./GooseForum migrate 显式执行。
  6. 启动并检查日志，验证登录、分类、主题、回复、附件和后台设置。

迁移失败时先保留错误信息，不要通过删除数据库或账号来让服务强行启动。历史用户名或邮箱规范化后冲突会导致唯一索引迁移失败，需要核对数据后解决。

恢复与回退 ​

先在隔离目录或测试机器恢复，避免测试实例发送真实邮件或误写线上对象存储。停止目标服务，恢复相同备份时点的配置、数据库和所需文件，修正路径与权限后再启动匹配版本。

数据库迁移后，仅换回旧二进制不保证能够回退。应恢复升级前的数据库与相关文件，并使用保留的旧程序；恢复旧快照会丢失快照之后的新写入，需先明确恢复时点。

恢复验收至少包括：账号登录与 MFA、旧主题和图片可读、发布与回复、后台权限、邮件发送、备份再次生成。恢复演练通过后，记录耗时和所用版本。

更新后浏览器仍显示旧内容 ​

主站和后台通过 /api/forum/status 检测部署变化，并提示用户刷新，不强制丢弃未保存内容。前端嵌入二进制，源码构建必须先构建前端再构建 Go 程序。刷新仍失败时检查代理缓存、静态资源请求和实际运行的程序路径。
